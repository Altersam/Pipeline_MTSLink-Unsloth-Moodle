# moodle-lesson-builder v2.3

Создаёт полноценные адаптивные HTML-уроки для Moodle из папок, содержащих `Расшифровка.txt`, `Запись.txt` и `files/`.

Поддерживает одиночный и пакетный режим, Windows-пути, безопасное возобновление, non-stop обработку и логическое обнуление контекста между уроками.

Главный принцип:

> **Один урок → анализ → план → HTML → проверка → статус → логическое обнуление → следующий урок.**

---

# 1. РЕЖИМЫ

## 1.1. Один урок

Если передана папка конкретного урока, обработай только её.

## 1.2. Пакет

Если передана родительская папка `.../уроки`, автоматически:

1. найди только непосредственные дочерние папки с числовым префиксом;
2. отсортируй их по числу `00 → 01 → 02 → ...`;
3. определи фактическое количество;
4. прочитай или создай `moodle_batch_status.json`;
5. обрабатывай строго по одному уроку;
6. продолжай автоматически до конца.

Не ожидай 17, 22, 27 или любое фиксированное число уроков. Не создавай отсутствующие номера искусственно.

---

# 2. WINDOWS-ПУТИ И СРЕДА ВЫПОЛНЕНИЯ

Исходная файловая система пользователя — Windows, но shell/tool-среда агента может быть Windows CMD, PowerShell, Python, WSL/Linux или проксированной файловой средой.

Переданный пользователем путь является каноническим.

Пример:

`Z:/YandexDisk/Лицей/.../уроки`

Проверять `ROOT_PATH` разрешено максимум в трёх формах:

1. ровно как передан;
2. с `/`;
3. с `\`.

Как только один вариант работает:

- зафиксировать его как `ROOT_PATH`;
- больше не переопределять;
- не менять букву диска;
- не менять имена каталогов;
- не искать другой корень.

Если `Z:/...` не открывается, запрещено автоматически предполагать `/mnt/z`, `/media/z`, `/run/media/...`, `/Z`, `C:/...` или другой диск.

Запрещено сканировать файловую систему ради поиска диска `Z:`.

Если `ROOT_PATH` недоступен после разрешённых проверок — остановить пакет и сообщить точную ошибку.

---

# 3. ЗАЩИТА ФАЙЛОВОЙ СИСТЕМЫ

Запрещены массовые рекурсивные обходы без явной необходимости:

- `find /`;
- `find /mnt`;
- `find /media`;
- рекурсивный `find` по `Z:`;
- обход всего `YandexDisk`;
- `Get-ChildItem -Recurse` по большим деревьям;
- `os.walk()` выше `ROOT_PATH`.

Для формирования очереди читать только непосредственные дочерние папки `ROOT_PATH`.

После определения `ROOT_PATH` использовать абсолютные пути. Предпочтительно не использовать `cd` между уроками.

Не повторять без причины `cd`, `pwd`, `ls`, `dir`, `find`, `cat`, `Get-ChildItem`.

Одна и та же неуспешная файловая операция может быть повторена максимум 2 раза после разумной коррекции синтаксиса.

Если недоступна отдельная папка урока — `needs_review`, сохранить конкретную ошибку и перейти дальше. Если недоступен сам `ROOT_PATH` — остановить пакет.

---

# 4. СОСТОЯНИЕ ОЧЕРЕДИ

Источник истины:

`moodle_batch_status.json`

Допустимые статусы:

- `queued`
- `in_progress`
- `done`
- `failed`
- `needs_review`

Если status-файл существует:

- не пересоздавай с нуля;
- `done` не трогай;
- сначала продолжай первый `in_progress`;
- если его нет — первый `queued`;
- при появлении новых папок добавь их, не сбрасывая старые статусы.

Перед началом урока:

1. поставить `status = in_progress`;
2. обновить `current`;
3. сохранить status;
4. работать только с текущим уроком.

После `done`, `failed` или `needs_review` немедленно сохранить status.

Для записи JSON предпочтительно: временный файл → проверка JSON → `replace/rename` в основной файл.

---

# 5. NON-STOP MODE

В пакетном режиме не возвращай промежуточный финальный ответ после каждого урока.

Пока существует хотя бы один `in_progress` или `queued`:

- продолжай tool calls;
- не жди сообщения `продолжай`;
- не спрашивай подтверждение;
- не останавливайся после одного урока.

Рабочий цикл:

`SAVE → QA → REPORT → STATUS → LOGICAL RESET → NEXT`

Промежуточный прогресс хранить на диске в status-файле. При необходимости вести `moodle_batch_progress.log`.

Финальный ответ пользователю разрешён только:

1. после завершения всей очереди;
2. если `ROOT_PATH` недоступен;
3. если сама среда технически не позволяет продолжить.

---

# 6. ОДИН УРОК = ОДИН РАБОЧИЙ КОНТЕКСТ

Для текущего урока загружать только:

- skill;
- краткое состояние очереди;
- `CURRENT_LESSON_PATH`;
- `Расшифровка.txt`;
- `Запись.txt`;
- содержательные материалы `files/`;
- существующий HTML этого же урока, если нужен.

После завершения урока:

- не перечитывать его transcript;
- не перечитывать его HTML;
- не переносить его предметный контекст;
- не переносить формулы, таблицы, SVG и черновики;
- не использовать tool-history предыдущего урока как рабочий материал.

Если среда умеет fresh context/subtask — использовать. Иначе выполнить логическое обнуление.

Между уроками сохраняются только skill, `ROOT_PATH`, status и общие технические правила.

Если контекст близок к пределу — сначала полностью закончить текущий урок, сохранить результат и статус, затем fresh context/logical reset. Не начинать новый урок на почти заполненном контексте.

# 7. ЧТЕНИЕ МАТЕРИАЛОВ

Для текущего урока найти:

- `Расшифровка.txt`;
- `Запись.txt`;
- `files/`;
- при наличии — старый `lesson.html`, `lesson_improved.html` и другие материалы.

Не открывать материалы следующего урока заранее.

## 7.1. Расшифровка

Желательно читать целиком. Если слишком большая — прочитать начало, середину, конец и ключевые участки с заданиями, формулами, примерами и вопросами.

Определить:

- предмет;
- класс;
- фактическую тему;
- подтемы;
- понятия;
- определения;
- формулы;
- алгоритмы;
- факты;
- примеры учителя;
- вопросы учеников;
- задания;
- типичные ошибки;
- домашнюю работу, если упомянута.

Главный источник темы — `Расшифровка.txt`. Имя папки — вспомогательный источник.

## 7.2. Запись

Прочитать `Запись.txt`. Использовать только реально присутствующие URL.

Видео — в самом начале урока, адаптивно 16:9. Под iframe добавить обычную ссылку.

Не придумывать URL.

## 7.3. files/

Изучить содержательные материалы текущего урока. Использовать их для теории, примеров, заданий, таблиц, схем и иллюстраций.

Не вставлять в Moodle локальные ссылки `C:\...`, `Z:\...`, `file:///...`, `./files/...`.

Контекст произведения, персонажи, темы, мотивы, композиция, анализ эпизодов, вопросы. Не цитировать большие фрагменты.

Корректная терминология, строение и функции, процессы, классификации, таблицы и SVG. Логика: `структура → функция → механизм → результат`.

Объекты, факторы, регионы, связи, диаграммы, таблицы, статистика, расчёты. Не рисовать вымышленную географию.

Модели, данные, обучение, инференс, генеративный ИИ, LLM, промпты, галлюцинации, проверка фактов, безопасность, приватность, этика.

## Проектная деятельность в сфере ИИ

Проблема, аудитория, цель, гипотеза, данные, MVP, тестирование, критерии успеха, риски, этика, защита проекта.

# 11. SVG, ГРАФИКИ И ВЫЧИСЛЕНИЯ

SVG использовать только с образовательной пользой.

Каждый SVG должен иметь `viewBox` и адаптивные размеры:

```html
<svg viewBox="..." style="width:100%; max-width:100%; height:auto;">
```

Без внешнего JS и CSS.

Для графиков вычислять и проверять точки, подписывать оси, не обрезать важные элементы.

Все числовые вычисления в математике, физике, информатике и других вычислительных дисциплинах проверять через Python, включая промежуточные шаги, округление и единицы измерения.

# 12. ДИЗАЙН

Каждый урок должен иметь собственную яркую, но не перегруженную палитру.

Баланс:

- 70–80% — светлые нейтральные поверхности;
- 15–20% — основной цвет;
- 5–10% — акценты.

Использовать:

- яркий hero;
- карточки;
- цветные левые границы у определений;
- отдельные блоки примеров;
- практику;
- типичные ошибки;
- итоговый блок;
- лёгкие inline-тени;
- `border-radius:12px–20px`;
- не более 2–3 градиентов.

Сохранять `color_theme` в `lesson_build_report.json`.

---

# 13. HTML-ТРЕБОВАНИЯ MOODLE

Итог — только HTML-фрагмент.

Запрещено:

- `<html>`;
- `<head>`;
- `<body>`;
- `<style>`;
- `<script>`;
- JavaScript;
- event handlers;
- `width:100vw`;
- глобальный `overflow-x:hidden`;
- локальные файловые URL.

Все стили только inline.

Корневой контейнер:

```html
<div style="width:100%; max-width:100%; box-sizing:border-box; min-width:0; overflow-wrap:anywhere; font-family:Arial,Helvetica,sans-serif; line-height:1.6;">
```

Широкие таблицы помещать в `overflow-x:auto`.

Код — в прокручиваемый `<pre>`.

Не оставлять сырой LaTeX, который Moodle может не отрисовать. Простые формулы — HTML/Unicode, сложные — HTML или SVG.

---

# 14. СОЗДАНИЕ И СОХРАНЕНИЕ HTML

Если `lesson.html` отсутствует — создать `lesson.html`.

Если существует и требует улучшения — создавать `lesson_improved.html`, затем `lesson_improved_2.html` и т. д.

Не писать HTML десятками мелких append-операций.

Предпочтительный цикл:

`READ → ANALYZE → PLAN → BUILD → WRITE → READ BACK → QA → FIX`

Для большого HTML предпочтительно:

1. сформировать основной контент;
2. записать во временный файл в той же папке;
3. проверить, что он читается и ненулевой;
4. заменить итоговый файл одной операцией, если возможно.

Это особенно важно в папках YandexDisk.

После сохранения обязательно прочитать начало, середину и конец файла и убедиться, что он не оборван.

# 15. QA ПЕРЕД DONE

Проверить:

## Содержание

- тема по расшифровке;
- предмет и класс;
- видео в начале;
- подробная теория;
- определения;
- формулы;
- примеры;
- практика и ответы;
- типичные ошибки;
- схемы/таблицы при необходимости;
- источники, если был Search;
- собственная цветовая тема.

## HTML

- нет `<html>`, `<head>`, `<body>`, `<style>`, `<script>`;
- нет JS-обработчиков;
- стили inline;
- корневой контейнер `width:100%`, `max-width:100%`, `box-sizing:border-box`, `min-width:0`;
- нет `width:100vw`;
- нет глобального `overflow-x:hidden`;
- нет сырого LaTeX;
- нет локальных файловых URL.

## Файл

- существует;
- размер > 0;
- UTF-8;
- прочитан обратно;
- не оборван;
- основные теги закрыты.

Только после этого `status = done`.

# 17. ОШИБКИ И ВОЗОБНОВЛЕНИЕ

Если отдельный урок невозможно обработать:

```json
{
  "status": "needs_review",
  "error_type": "filesystem_access",
  "error": "Конкретное описание"
}
```

или `failed` для ошибки обработки.

После фиксации причины перейти к следующему уроку.

При новом запуске:

1. прочитать `moodle_batch_status.json`;
2. взять первый `in_progress`;
3. если нет — первый `queued`;
4. `done` не трогать;
5. если у `in_progress` есть частичный HTML — сначала проверить его и продолжить, а не делать всё заново.

# 21. КРИТЕРИЙ УСПЕХА

Навык выполнен правильно, если:

- количество уроков определено автоматически;
- каждый урок обработан отдельно;
- порядок не нарушен;
- HTML основан на конкретной расшифровке;
- после каждого урока сохранён статус;
- можно безопасно продолжить после перезапуска;
- `done` не перерабатываются;
- HTML пригоден для Moodle;
- уроки содержательны и адаптированы к предмету;
- агент не ждёт команды `продолжай`;
- агент не сканирует диски и mount points без разрешения;
- агент не перегружает файловую систему рекурсивными обходами;
- завершённый урок логически удаляется из рабочего контекста перед следующим.


# 20A. ПРОВЕРЕННЫЙ MOODLE/WAF SAFE PROFILE — КРИТИЧЕСКОЕ ПРАВИЛО

Этот профиль имеет приоритет над любыми требованиями «сделать интерактивнее».

Экспериментально подтверждено, что Moodle принимает обычный HTML-фрагмент с inline CSS, таблицами, `<pre>`, SVG и проверенным iframe записи, но более «веб-приложенческие» конструкции могут вызывать WAF/XSS-защиту.

## 20A.1. Разрешённый базовый подход

Используй обычный Moodle-safe HTML:

- `<div>`
- `<p>`
- `<h1>`–`<h4>`
- `<span>`
- `<strong>`
- `<em>`
- `<ul>`, `<ol>`, `<li>`
- `<table>`, `<thead>`, `<tbody>`, `<tr>`, `<th>`, `<td>`
- `<details>`, `<summary>`
- `<pre>`, `<code>`
- `<a>`
- `<img>` — только с реальным доступным URL
- `<iframe>` — только для записи из `Запись.txt`
- статический встроенный `<svg>` и обычные SVG-фигуры

Все стили — только inline.

## 20A.2. Строго запрещено

Никогда не использовать:

- `<script>`
- `javascript:`
- любые обработчики событий:
  - `onclick`
  - `onload`
  - `onerror`
  - `onmouseover`
  - `onchange`
  - любые другие атрибуты `on...`
- `srcdoc`
- `data:text/html`
- inline JavaScript в любом виде
- JS-обёртки вокруг iframe
- `<object>`
- `<embed>`
- `<applet>`
- `<form>` и активные формы без отдельного запроса
- скрытые элементы, имитирующие выполнение кода
- конструкции, похожие на XSS/injection
- внешние `<style>`
- внешние JS-библиотеки
- самописные виджеты, требующие выполнения JavaScript

Если интерактивность требует JavaScript — НЕ ДЕЛАЙ её.

Используй вместо этого:

- `<details>/<summary>`;
- статические SVG;
- таблицы;
- карточки;
- пошаговые схемы;
- визуальные последовательности;
- несколько состояний, показанных рядом;
- статические графики.

## 20A.3. Python и другой программный код

`<pre>` и `<code>` разрешены.

Но код внутри HTML должен быть показан как ТЕКСТ, а не интерпретироваться браузером.

Если пример содержит HTML/XML/JS-подобные конструкции, обязательно экранируй:

- `&` → `&amp;`
- `<` → `&lt;`
- `>` → `&gt;`

Пример:

```html
<pre style="..."><code>if x &lt; 10:
    print("OK")</code></pre>
```

Нельзя вставлять внутри `<pre>` сырой `<script>` или другие активные теги даже как «пример кода».

## 20A.4. iframe записи

`<iframe>` разрешён только для ссылки/iframe из `Запись.txt`, если такой вариант уже используется в рабочем Moodle.

Используй простой iframe без JavaScript-обвязки:

```html
<div style="width:100%; box-sizing:border-box; margin-bottom:24px;">
  <div style="position:relative; width:100%; padding-top:56.25%;">
    <iframe
      src="REAL_URL_FROM_ЗАПИСЬ_TXT"
      style="position:absolute; inset:0; width:100%; height:100%; border:0;"
      allowfullscreen>
    </iframe>
  </div>
  <div style="margin-top:8px; overflow-wrap:anywhere;">
    <a href="REAL_URL_FROM_ЗАПИСЬ_TXT" target="_blank" rel="noopener noreferrer">
      Открыть запись занятия
    </a>
  </div>
</div>
```

Запрещено добавлять к iframe:

- `onload`;
- JS для resize;
- JS для autoplay;
- JS-обёртки;
- `srcdoc`;
- неизвестные URL;
- придуманные параметры.

## 20A.5. SVG

Используй в первую очередь статический SVG.

Не использовать внутри SVG:

- `<script>`;
- обработчики `on...`;
- внешние JS;
- ссылки `javascript:`;
- `<foreignObject>` без крайней необходимости;
- активные/скриптовые конструкции.

Для максимальной совместимости Moodle/WAF избегай SVG-анимации (`<animate>`, `<animateTransform>`) по умолчанию.

Если нужна «анимация», лучше показать:

- 3–5 последовательных статических кадров;
- стрелки направления;
- numbered steps;
- timeline;
- before/after;
- progressive diagram.

## 20A.6. CSS

Допустим только inline CSS в `style=""`.

Не использовать:

- `<style>`;
- `@import`;
- `@keyframes`;
- внешние stylesheet;
- CSS, требующий внешних ресурсов;
- сложные трюки, похожие на UI веб-приложения.

Допустимы:

- flex;
- grid, если Moodle сохраняет;
- `clamp()`;
- градиенты;
- border-radius;
- простые тени;
- адаптивные размеры;
- overflow-x:auto для таблиц и кода.

Если сложный CSS не нужен для понимания урока — не использовать.

## 20A.7. Ссылки и изображения

В итоговом HTML запрещены:

- `file:///...`
- `Z:\...`
- `C:\...`
- `./files/...`
- придуманные URL

Разрешены только:

- реально существующие `http://`/`https://` ссылки;
- URL из `Запись.txt`;
- реальные внешние изображения, если источник доступен и использование уместно.

Если нет надёжного URL картинки — лучше сделать собственную SVG-схему, чем вставлять битую ссылку.

## 20A.8. Приоритет безопасности над интерактивностью

Если есть выбор между:

A. красивым, но потенциально блокируемым Moodle/WAF интерактивом;

и

B. чуть менее интерактивным, но гарантированно безопасным HTML + inline CSS + SVG + table + pre;

всегда выбирай **B**.

Проверенный стандарт проекта:

> **HTML-фрагмент + inline CSS + таблицы + статический SVG + `<pre>/<code>` + `<details>/<summary>` + простой iframe записи. Без JavaScript.**
